# Deployment

| Part     | Host          | Config in repo                  |
|----------|---------------|---------------------------------|
| Frontend | Vercel        | `frontend/latest/vercel.json`   |
| API      | Render        | `render.yaml`                   |
| Database | MongoDB Atlas | —                               |

## Current deployment (portfolio prototype)

| | |
|---|---|
| Site | https://mandela-school.vercel.app (Vercel project `mandela-school`, root `frontend/latest`) |
| API  | https://mandela-school-api.onrender.com (Render Free, Frankfurt, auto-deploys `main`) |
| Database | Atlas `Cluster0` (Free, AWS eu-west-1), database `mandela-school`, user `mandela-api` with `readWrite` on that database only |
| Email | Brevo Free over `smtp-relay.brevo.com:2525` |

The Render service was created through Render's API with the same settings as
`render.yaml`, in Frankfurt to sit next to the Atlas cluster; it is not linked as a
Blueprint, so edit its environment in the dashboard. All data is simulated; the only
account is a demo headteacher whose credentials live in the gitignored `backend/.env`.

**Seeding from Windows:** if `npm run seed:admin` against Atlas fails with
`querySrv ECONNREFUSED`, the local resolver is refusing SRV lookups. Run it through a
public resolver for that one process, e.g. a preload file containing
`import dns from 'node:dns'; dns.setServers(['1.1.1.1']);` passed with `node --import`.

## Setting it up from scratch

The two apps live on different domains, so each needs the other's URL: the frontend
gets the API's address at **build time** (`VITE_API_URL`), and the API gets the site's
address as its CORS allow-list (`CORS_ORIGIN`). Follow the steps in order.

## 1. Database — MongoDB Atlas

1. Create a free (M0) cluster.
2. **Database Access** → add a user with a generated password.
3. **Network Access** → allow `0.0.0.0/0`. Render's free and starter plans have no fixed
   outbound IP, so there is nothing narrower to allow; the database user's password is
   the protection.
4. **Connect → Drivers** → copy the connection string and put a database name before the
   `?`, e.g. `mongodb+srv://user:pass@cluster0.xxxxx.mongodb.net/mandela-school?retryWrites=true&w=majority`.

## 2. Email — Brevo on port 2525

Render's **free** plan silently drops outbound SMTP on ports 25, 465 and 587, so email
goes through Brevo's relay on **2525**, which the free plan allows. Brevo's free tier
sends ~300 emails a day. `render.yaml` already sets the host and port.

1. Create a Brevo account.
2. **Senders, Domains & Dedicated IPs → Senders** → add and verify the address parents
   will see mail from (Brevo emails it a confirmation link). This becomes `EMAIL_FROM`.
   Verifying the whole domain (SPF/DKIM DNS records) instead improves deliverability, but
   is optional.
3. **SMTP & API → SMTP** → note the **Login** (looks like `xxxx@smtp-brevo.com`) and
   generate an **SMTP key**. These become `EMAIL_USER` and `EMAIL_PASS`.

The SMTP login is not a mailbox and must not be the from-address; Brevo rejects mail
that is not from a verified sender.

## 3. API — Render

1. Push the repo to GitHub.
2. Render → **New → Blueprint** → select the repo. It reads `render.yaml`.
3. Fill in the values it asks for:

   | Variable       | Value                                                     |
   |----------------|-----------------------------------------------------------|
   | `MONGO_URI`    | Atlas string from step 1                                  |
   | `CORS_ORIGIN`  | `http://localhost:5177` for now; replaced in step 5       |
   | `EMAIL_USER`   | Brevo SMTP login from step 2                              |
   | `EMAIL_PASS`   | Brevo SMTP key from step 2                                |
   | `EMAIL_FROM`   | The verified sender from step 2                           |
   | `ADMIN_EMAIL`  | Inbox that receives new-enquiry alerts                    |

   `JWT_SECRET` is generated by Render; `NODE_ENV`, `TRUST_PROXY` (3) and `SCHOOL_NAME` are
   set by the Blueprint.
4. Once it deploys, open `https://<service>.onrender.com/`. It should show
   `{"status":"API running"}`. Note this URL.

On the free plan the service sleeps after 15 minutes idle; the first API call after that
takes 30–60 seconds. The public pages are unaffected (they are served by Vercel), but
the enquiry form, news, events and admin login wait for it to wake.

## 4. Frontend — Vercel

1. Vercel → **Add New → Project** → import the repo.
2. **Root Directory**: `frontend/latest`. Vercel detects Vite; leave the build settings
   at their defaults.
3. **Environment Variables**: `VITE_API_URL` = `https://<service>.onrender.com/api`.
4. Deploy and note the URL, e.g. `https://mandela-school.vercel.app`.

`VITE_API_URL` is baked in when the site is built. If it ever changes, redeploy the
frontend; editing the variable alone does nothing to the live site.

## 5. Connect the two

In Render → the service → **Environment**, set `CORS_ORIGIN` to the Vercel URL. Use
exact origins with no trailing slash, comma-separated if there are several (e.g. a
custom domain as well):

```
https://mandela-school.vercel.app,https://www.mandelaschool.example
```

Render redeploys automatically on save.

## 6. Create the first login

The seed script reads credentials from `backend/.env` only, so the password never lands
in shell history. Point it at production for one run:

1. In `backend/.env`, temporarily set `MONGO_URI` to the Atlas string, and set
   `ADMIN_SEED_EMAIL`, `ADMIN_SEED_PASSWORD` (12+ characters) and
   `ADMIN_SEED_ROLE=headteacher`. Only a headteacher can manage staff accounts.
2. Run `npm run seed:admin --prefix backend`.
3. Put `MONGO_URI` back to your local database and clear `ADMIN_SEED_PASSWORD`.

Do **not** run `seed:demo` against production; it fills the dashboard with invented data.

## 7. Check it works

- [ ] Home page loads; refreshing `/admissions` and `/admin/login` does not 404
- [ ] Submit an enquiry → success message, and the alert arrives at `ADMIN_EMAIL`
- [ ] Log in at `/admin/login` → the enquiry is in the inbox
- [ ] Reply to it → the parent address receives the email and the status turns `replied`
- [ ] Publish a news article → it appears on `/news`

## Updating

Both hosts redeploy on every push to `main`. The API refuses to start if `JWT_SECRET` is
missing or still the `.env.example` placeholder, so a misconfigured deploy fails loudly
in Render's logs rather than serving a broken or forgeable login.
